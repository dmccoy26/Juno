# Operational evidence and planning — source candidate

This work extends the existing architecture. It is source code only: no app installation, package or ZIP was built for Mission 13. The installed preview.21 workspace remains separate and unchanged. Migration 0013 is additive and is exercised only in disposable test databases during development.

## Read-only workflow

After normal authorized TaskDock and Beacon refreshes, Daily check-in shows **Equipment & linked work · saved evidence**. Existing questions still appear first. Each observation lists its evidence, source timestamps, recorded work, explicitly shared impact/authority, next recorded action, contradictions and missing identifiers. **View evidence** reads the exact owner-authorized saved snapshot/record. A source refresh or sharing withdrawal can make that record unavailable; another record is never substituted. Producer-relative Beacon links are preserved as metadata, never fetched automatically.

Use **Review alert–task links…** on the work Mac. Search task titles or exact references; choose a Beacon alert and TaskDock task, review why they belong together, then save. This records an exact-ID relationship in Juno, not an assignment or a durable Beacon issue. Saving replaces the earlier relationship for that alert; Remove withdraws the reviewed reference. Snapshot, workspace and local revision changes reject stale saves. Missing observations/tasks and changed rooms remain explicit. No names, titles or room labels create a link automatically.

Task closure, an acknowledged issue and verified equipment recovery are independent. An unfinished task after a reported recovery is a contradiction to review; a completed task with unknown/failed verification does not establish healthy equipment. Unknown authority is not permission. The current Beacon feed does not supply the durable asset/issue/recovery/authority fields needed for a live linked-pilot signoff.

## Planning and feedback

Plan preserves existing Dean/operations ranking and dated overrides. It shows source-backed service-impact reasons, blocks repairs with contradictory/stale linked evidence or an explicit department-lead decision requirement, and continues enforcing existing missing-data checks. Qualification decisions remain reviewed Juno facts until TaskDock supplies a supported qualification contract.

**Coordinated work proposal** allocates feasible ranked work across recorded intervals without repeating the same person/room/owner time. It accounts for supervision, remaining personal capacity and employee weekly limits including existing holds. A pending priority/readiness question suppresses the proposal. This is a greedy proposal, not an optimized semester plan, saved assignment or simultaneous interpretation of alternatives. Missing calendars/qualifications remain limitations.

**Record planning choice…** records accepted, dismissed or rescheduled feedback and an optional reason. It does not book time, reserve a room, assign a worker or change a due date. Accepted feedback requires an actionable proposal and resolved planning question. A reschedule requires a valid proposed date. Snapshot/planning/revision fences reject stale feedback. Retrying the same operation recovers its existing receipt; a changed payload cannot reuse that identity. Uncertain requests keep the same identity while the sheet is open. If closed after an uncertain save, inspect Recent planning choices before submitting again. History is retained, not silently pruned; its explicit capacity bound stops new writes rather than deleting older feedback.

## Weekly drafts

Preparation adds decisions/agenda, unresolved operational issues, source record references and missing milestone coverage. Beacon snapshot/error/freshness and local relationship revision join the draft evidence basis. Refreshing evidence marks saved drafts changed, without overwriting reviewed writing. Existing recovery, comparison and revision checks remain intact. Nothing is automatically sent. Source records are evidence for review; the generated text is a draft.

## Procedures and lifecycle

**Procedures & longer-term repair review** uses only already-authorized saved TaskDock evidence, Slack, Smartsheet, Gmail or Google Chat records. Designate a reference by source, snapshot and record ID. Its current text, retrieval/update metadata and changed/stale/missing status stay visible. Selection does not establish official approval. No linked URL/attachment is fetched and document content grants no authority. Disconnecting/removing a source withdraws its text; retained references cannot reconstruct it. Local-model context receives bounded references with these warnings; source and reference changes invalidate dependent replies. A full linked-document reader still needs designated locations and authorized document APIs.

Recurring reviewed repairs can appear as investigation candidates with supporting report references. They explicitly lack stable asset identity/current condition/usage/cost/policy when those inputs are unavailable. No replacement/purchase decision or failure date is inferred. No TaskDock task is created.

## Access and limits

New relationships, procedure designations and feedback are work-Mac-only writes. Connected paired laptops can read operational evidence through the existing owner-authenticated TLS boundary. No new worker-portal route or access is granted. Operational panels are not new offline caches or queues; reconnect to refresh them. Existing offline diary/memory behavior is unchanged. Records remain owner-scoped and bounded (500 links, 200 procedure references, 2,000 feedback receipts); hitting a bound retains history and reports a failure.

See the [shared contract and external dependencies](OPERATIONAL-CONNECTION-CONTRACT.md). Live printer pilot, producer contract agreement, TaskDock writes, source qualification/milestone integration, authoritative staffing coverage, current lifecycle facts and linked-document API acceptance remain external gates. Synthetic consumer tests do not establish those integrations.
